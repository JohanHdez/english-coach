# The live line: implementation plan

Revision 2. The first revision was reviewed and three things were wrong: step 3's commit rule
does not work with the tail window, the rejection of overlap stitching rested on a cost that
does not exist, and the order did not attack the growing translation cost first. Corrected below;
what changed is recorded at the end.

The provisional line is the text that shows what the other person is saying *while* they say it.

## Three costs that grow with the length of the line

Only the first was addressed, and addressing it opened a hole.

1. **Whisper re-transcribes a growing buffer.** Fixed by `PREVIEW_TAIL_MS`. That fix means a
   phrase running between 8 s and `MAX_SEG_MS` = 18000 has a head that has left the provisional
   line and has not reached the transcript bubble — for up to ten seconds those words are nowhere
   on screen.
2. **The translation is redone over the whole line on every `PARTIAL`.** O(n) per update, O(n²)
   accumulated over a monologue. This is the cost felt in the Spanish line and it is untouched.
3. **`textContent = text` replaces the whole node on every update.** Cosmetic, but it is part of
   what reads as the line jumping.

## The measured defect behind step 3

`tail()` returns the whole buffer while the phrase is under the window and slides once it is
past. Driving the real segmenter with 17 s of unbroken speech:

```
pass  dur(ms)  first block   same start as previous?
   5     7200    preroll       yes
   6     8400          3       NO
   7     9600         15       NO
   8    10800         27       NO
```

From 8.4 s each pass begins 12 blocks (1.2 s) later than the last. **A longest-common-prefix
commit rule therefore yields an empty prefix in exactly the case it exists for.** The first
revision of this plan specified that rule; it does not work.

What does work is overlap alignment: match the *suffix* of the accumulated text against the
*prefix* of the new pass. And it delivers a second rule for free — whatever sits before the
alignment point is text whose audio has left the window, which no future pass can ever see again,
so it is final by construction. There is no word-to-time mapping in this pipeline
(`worker.js` sends `return_timestamps: false`), so "older than the window" cannot be evaluated
directly; alignment is how it is evaluated.

## Step 1 — Define the two-field `PARTIAL`

**Goal.** Fix the display contract before anything produces or consumes it, so the two sources in
steps 2 and 4 cannot invent different shapes.

**Change.** `PARTIAL` carries `committed` (settled, never changes again) alongside `text`. Define
it in `.claude/skills/message-contract/SKILL.md` first, including how it interacts with rule 8:
splitting the payload does not make any of it persistent, cached in `lastUi`, or visible to the
report. Render committed in normal weight and the tail dimmed, in `overlay.js` and `sidepanel.js`
— the overlay keeps its own copy, it cannot import.

**Why first.** It is cheap, it is the part of the old step 2 that carried the value, and it does
not depend on Web Speech being alive.

**Done when** both views render a two-part provisional line and preflight's protocol check passes.

---

## Step 2 — Commit by overlap alignment

**Goal.** The provisional line only ever changes at its end, and the head stops disappearing.

**Change.** A pure function that takes the accumulated text and a new pass, aligns the new pass's
prefix against the accumulated suffix, and returns `{committed, volatile}`:

- text before the alignment point is committed — its audio has left the window;
- text after it is committed once it has agreed across two consecutive passes;
- everything else is volatile.

**Where it lives.** Its own pure module with its own tests. Not inside `offscreen.js`.

**This closes the coverage hole from the display side**, without touching segmentation: the head
that leaves the window is already committed on screen, so it does not vanish. That is why the cut
change is now conditional and last.

**Failure modes the tests must cover.**
- Alignment finds no overlap (Whisper produced very different text): the previous committed text
  must be kept and only the volatile part replaced — never silently dropped.
- A word genuinely repeated by the speaker: must not collapse into one.
- A hallucinated repetition loop: confirm `isJunk` fires *before* the commit rule, or a loop gets
  committed permanently.
- A boundary word cut mid-syllable by the window: must not commit.
- `flush()` empties `chunks` at every cut, so **the committed text must reset per phrase** or the
  next phrase inherits the previous one's prefix.

**To calibrate.** Two passes is a guess, but the age rule bounds the damage: even if the number is
wrong, text commits by leaving the window. Measure it, do not pick it from memory.

**Fallback if string alignment proves fragile.** Chunk-level `return_timestamps` in `worker.js` is
nearly free — decoded tokens, not the word-level DTW that would blow `PREVIEW_MAX_MS` — and
replaces alignment with time anchoring, which removes the repetition failure modes outright.

**Done when** a 17-second monologue leaves no words off screen and nothing above the commit point
ever changes.

## Step 3 — Anchor translation to the commit

**Goal.** Remove the O(n²) and stop the Spanish reflowing end to end.

**Change.** In `showPartial` (`overlay.js` and `sidepanel.js`, one copy each): translate the
committed prefix once, cache it by its English text, and re-translate only the volatile tail.
`translate.js` is untouched.

**The commit is the boundary, not punctuation.** Clause detection still earns its place — it
splits the committed prefix into cacheable units — but what guarantees that translated text never
moves is that the English behind it can no longer change. Punctuation alone does not guarantee
that: a clause inside the volatile region is still subject to revision.

Two adjustments that go with it:
- debounce the tail translation by 250–300 ms rather than translating on every `PARTIAL`;
- skip tails of one or two words — they give the translator no context to disambiguate with, and
  spend a call to produce noise.

**Done when** the Spanish grows left to right, previously translated text never moves, and the
per-update cost no longer scales with the length of the line.

---

## Step 4 — Read `isFinal` in `live.js`

**Goal.** The same two fields, from the source that already knows the answer.

**Change.** `emit()` concatenates every result from `base` with no finality check. Split the walk
on `results[i].isFinal` and emit the committed prefix and the volatile tail into the contract from
step 1.

**Why fourth.** The API marks this natively and throwing it away is a real defect, but it applies
only where Web Speech is alive — which is not the reported case. After step 2 it is a refinement
for other users, not the fix for this one.

**Done when** a session on a machine with working on-device recognition shows a settled prefix and
a dimmed tail, with the tail the only thing that changes.

---

## Step 5 — Bound the phrase to the window, only if still needed

**Conditional.** Do this only if, after step 2, a real session still shows words off screen.

**Why conditional.** It changes how the persisted transcript is segmented, which is visible in the
report. Step 2 solves the same symptom in the display layer without touching persistence, so this
is the more invasive of two fixes for one problem.

**If it is needed, do not cut at a fixed instant.** A hard cut at exactly 8 s cuts through words
just as the fine ladder did — a `CHUNK_MS` boundary is a 100 ms grid point and has nothing to do
with word boundaries. Cut at the **lowest-energy block within the last 1–1.5 s of the window**.
Still one rung; it just looks for the best available pause instead of taking whatever is at 8 s.

**Tests** in `segmenter.test.js` beside the existing tail tests: no piece exceeds
`PREVIEW_TAIL_MS`, the normal soft cut still wins when a real dip exists, and the chosen block is
the quietest in the search range.

## Rejected, with the reason

| Option | Why not |
|---|---|
| Translate every three words and concatenate | Agreement, clitic position and adjective order are decided inside that window. The commit point is the correct boundary. |
| Switch the trigger from time to word count | The Whisper lane emits one string per pass. There are no words to count until it returns, and the two lanes are mutually exclusive by design. |
| Adopt `WhisperTextStreamer` now | Already vendored and free, but it only shortens time-to-first-word *within* a pass. It does not make the display append-only. Separate, later. |

Overlap stitching is **no longer rejected** — it is step 2. The first revision rejected it on the
grounds that it would cost latency on the English line. That cost belongs to a design that
withholds text until it is confirmed; the alignment computation itself is microseconds over a few
hundred characters. The reasoning was wrong.

## What cannot be verified statically

Preflight checks syntax, the manifest, CSP, the protocol and dead code. It cannot verify that
audio is captured, that WebGPU answers, that Chrome's Translator responds, or that any of this
looks right. Four things to measure in a real session rather than assume:

1. the delay before the first preview of a turn (`PREVIEW_MIN_MS` gates the first ~1.2 s);
2. how often the slowness guard trips now that it counts consecutive rounds;
3. how many passes a prefix must agree on before committing is safe;
4. **Spanish-line latency as a function of line length, before and after step 3** — the direct
   measurement of the O(n²) claim, and the only way to know whether step 3 delivered.

## Revision 3 — the line must never go blank while someone is talking

Field report (2026-09-02), after steps 1 and 2 were applied: the live line still *disappears*
whenever a turn is delivered into its bubble, the other speaker's next phrase shows nothing until
that delivery is done, and the learner's own speech has no live line at all. The tester's
priority is explicit: the live text always, immediately, for both voices; the authoritative
transcript and the translation may lag behind it.

Three defects, and what replaced them:

| Defect | Fix |
|---|---|
| Every delivered `them` turn blanked the line — even a soft cut, with the speaker mid-sentence | The segmenter now marks each segment `open` (soft/hard cut) or closed (real pause). Only a closed turn blanks the line; an open one leaves it standing until the next piece's preview repaints it. Web Speech keeps its reset on every turn — word-by-word refills within a word, and without the reset the line would re-grow text already in the bubble |
| Previews were refused while the engine had any real work (`previewReady` required an idle queue), so the gap between cut and delivery had no live text by construction | Priority inverted, in `queue.js` (pure, tested): previews go ahead of queued real segments, at most one queued per speaker (a fresher offer replaces the stale one, a real segment evicts its own speaker's) — and on a budget. Review simulation showed one queued slot does *not* bound the passes a real segment yields to: on an engine whose pass costs about `PREVIEW_EVERY_MS` the slot refills before the queue drains, and with both lanes talking the first real segment of a session never ran. `MAX_PREVIEW_BYPASS` caps the total passes run ahead of any real segment; spent, it moves ahead of new previews |
| The microphone had no provisional lane (`onPreview: null`) | Both segmenters preview. `PARTIAL` now carries `speaker`, the offscreen document stitches one line per voice (keyed by the piece's `startedAt`, so a new piece cannot inherit a committed prefix), and both views render a second, learner-styled line — English only, since the learner needs no translation of what they just said |

## Revision 4 — what the numbers said, and what is actually left

Both specialists were consulted on how to close the remaining latency, cross-examined against
each other, and both revised their first answer. Three measurements settled it; two of them
contradicted a specialist's own premise, which is why they are recorded here as tests rather
than as prose.

**Measurement 1 — `PREVIEW_MIN_MS` was never the floor.** Driving the real segmenter and
timing from voice onset: the first preview of a piece lands **400 ms** after onset, in a
700 ms buffer, and setting `previewMinMs` to 700, 600, 500, 400, 300 or 200 does not move it
by one block. `MIN_VOICED` (5 voiced blocks) is the binding constraint, and the buffer it
arrives in already carries `PREROLL - 1` blocks of lead-in, so the duration floor is satisfied
by the same block that satisfies the voiced floor. The previous estimate of "700 ms gate +
pass ≈ 1.2–1.5 s to first text" was wrong on its first term. `PREVIEW_MIN_MS` is now 500 — a
latency win of **zero ms**, kept only so that the day `MIN_VOICED` is lowered to cut the
400 ms, a second hidden floor at 700 does not silently swallow the gain. Pinned by
`the voiced-block floor gates the first preview, not PREVIEW_MIN_MS`.

**Measurement 2 — the real bottleneck is a queue stall nobody had modelled.** `insertPreview`
reorders the queue array, but `drain()` is single-flight: a preview cannot preempt a pass
already running, and real passes have no `PREVIEW_MAX_MS` equivalent. Driving the segmenter
shows a real segment reaches the full `MAX_SEG_MS` = 18 s whenever the speaker's dips stay
under `SOFT_SILENCE_MS`: at 300 ms dips the soft cut works (max piece 6.6 s), at **200 ms dips
it does not** (max piece 18 s). Voiced filler — "um", a held vowel — resets the silence
counter, so a hesitant learner, this product's own user, is the pathological case rather than
an edge case. On the WASM fallback a preview queued behind such a pass waits it out entirely.

**Measurement 3 — bounding it costs nothing visible.** The obvious fix is lowering
`MAX_SEG_MS`, and the forced-cut branch needs no dip, so it is a hard ceiling rather than a
statistical hope. Its feared cost — a fragmented transcript — does not exist: running the
emitted pieces through `foldIntoTranscript`, a 60 s monologue produces **3 displayed turns at
an 18 s cut and 3 at an 8 s cut**; 30 s produces 2 either way. `MERGE_MAX_CHARS` decides turn
boundaries, not the cut. The cost is more intermediate `SEGMENT` broadcasts and more, shorter
worker calls — not anything the learner reads.

### Shipped in this revision

| Change | Where | Effect |
|---|---|---|
| Per-lane `previewSlow` / `previewOff` | `offscreen.js` | One voice's two slow passes no longer retire the other voice's live line. The `slow` notice now fires only once **no** voice has a live lane left (`anyLiveLaneLeft`), because announcing "no live transcription" while text is still appearing for the other speaker reads as a broken extension |
| `PREVIEW_MIN_MS` 700 → 500 | `segmenter.js` | No latency change (measurement 1); removes a hidden second floor |
| Terminal-only listener teardown | `offscreen.js` `localTranscribe` | `removeEventListener` ran before the type check, so any future non-terminal worker message for a live id would drop the result that follows it — promise never settles, `busy` never clears, whole queue stops for the session. A strict no-op today (the worker sends only `result`/`error` with an id; `progress`/`ready` carry none) |

### Not done, and why

- **Lower `MAX_SEG_MS`** — measurement 3 says it is nearly free and it is the only construction-level
  bound on the stall. It changes how the persisted transcript is segmented, so it is the user's call.
- **Instrumentation** — both specialists independently landed on the same design: `console.debug`
  per pass in the offscreen document (queue wait, pass cost by lane, onset-to-first-text), read via
  `chrome://extensions` → *Inspect views: offscreen.html*, with a capped ring buffer and one
  `console.table` on `STOP`. Invisible to users by construction; no protocol surface. Rejected
  alternatives: a settings gate (a `chrome.storage` consideration on a hot path, per invariant 4)
  and `STATUS` messages (that *is* UI protocol surface and cannot produce a table).
- **Token streaming (`WhisperTextStreamer`)** — still the right eventual investment and the only
  option that helps where Web Speech is dead, but it shortens start-to-first-word, not wait-to-start.
  Its benefit is largest exactly where the stall is absent and smallest in the multi-second WASM
  stalls that actually break the requirement, so measuring it before the stall is bounded means
  measuring through a confound. When it is built: **only completed passes may feed `stitch()`**.
  Consecutive callbacks of one greedy decode are not independent evidence — they share their whole
  prefix by construction — so feeding them to the two-pass agreement rule would commit a single
  pass's hallucination permanently. The stream belongs on screen as a discardable overlay after the
  last completed pass, scoped to previews only, batched ~100–150 ms rather than per token.
- **Second Web Speech recognizer on the mic** — both specialists recommend against it, independently
  and for the same reason: on the reference machine Chrome's on-device recognizer already reports
  itself available and then never emits a word, so a second instance of the same engine most likely
  inherits the identical silent failure — paying a `LIVE_STATE`-per-speaker protocol change, doubled
  watchdog state and pause/resume symmetry for zero gain on the machine that motivated the request,
  while adding a second never-verified native engine to every session. Revisit only if a session on
  a machine where Web Speech *works* shows streamed Whisper still too slow.
- **Second dedicated Worker for previews** — removes the stall by construction on WebGPU, but on the
  WASM fallback it adds a second consumer of the one scarce resource (CPU) beside the realtime audio
  thread, so it can convert a queueing delay into a slower real pass. Roughly doubles resident model
  memory. Park behind measurement.
